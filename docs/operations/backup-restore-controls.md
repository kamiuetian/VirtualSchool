# Backup verification and controlled restore records

Only authenticated `PLATFORM_SUPER_ADMIN` operators may use the tenant-scoped `/api/v1/tenants/:tenantId/privacy/backup-operations` endpoints. A verification records backup type, provider name, an infrastructure-safe backup reference, creation and verification timestamps, expected interval, retention date, outcome, and an HTTPS evidence reference. The API derives `CURRENT`, `STALE`, or `FAILED` freshness without receiving provider credentials. Secret values, connection strings, access tokens, recovery keys, and evidence contents must remain in the approved infrastructure and evidence repositories.

Use `POST .../verifications` after checking the provider backup job. Use `POST .../restore-drills` to request a restore into `ISOLATED_TEST` or `STAGING`; production is deliberately not an accepted target. The request must reference a verified backup and an HTTPS runbook. A different platform administrator must approve it through `POST .../:drillId/approve` before the result can be recorded through `POST .../:drillId/complete`. This API records authorization and results; infrastructure restore execution remains an operator-run runbook step using the approved privileged tooling.

Every verification, request, approval, and completion writes a tenant-scoped audit event. Restore evidence should document integrity checks, application smoke tests, measured recovery time, cleanup of restored data, and follow-up actions. Failed checks must be recorded as `FAILED` rather than replaced with a newer successful record.
